	    <h2>Contracts Finder Update</h2>
	    <p>Contracts Finder API is updating. Version 2 of the API attempts to improve the structure and standardise approaches to aid the user in posting and retrieving notices. For more details, please visit <a href="/apidocumentation/V2">Version 2</a>.</p>
            
            <h2>Introduction</h2>
            <p>
                This document sets out to describe the mechanisms by which eOpportunity providers and others can feed their opportunities to the Contracts Finder Service.
                This can be done via this WebAPI individually at the point of publication, or via bulk import at a convenient time.
                Both mechanisms use common interfaces, with the latter accepting collections of data in one go.
            </p>
            <h3>Scope and purpose</h3>
            <p>The purpose of this document is to describe the interfaces available to approved external notice publication providers that enable them to publish their notices in the Contracts Finder service.</p>
            <p>Notice types that can be uploaded are:</p>
            <ul>
                <li>Future Opportunities, i.e. pre-procurement notices to publicise forthcoming activity</li>
                <li>Live Opportunities, i.e. invitations to tender</li>
                <li>Awards, i.e. transparency publications of awarded contract details</li>
                <li>Early Engagements, i.e. notices of intent which invite discussion on the way forward</li>
            </ul>
            <p>
                Whilst this is primarily a specification document to describe the inbound interface, some consideration shall be given to explain how particular aspects of the specification are handled by the inbound feed, specifically around the handling of category and region information.
                It shall describe, where appropriate, any specific data types and field length limitations placed upon external providers, in order that their opportunities are aggregated within the Contracts Finder service.
            </p>
            <p>This document shall provide an overview of how warnings and error messages shall be communicated to providers, but at this time shall not include specific warnings or errors.</p>
           <h2>Technical Specification</h2>
            <h3>REST</h3>
            <p>
                Representational State Transfer (REST) is an architectural style based on the architecture of the Web and embraces HTTP.
                Clients initiate requests to servers; servers process requests and return appropriate responses.
                Requests and responses are built around the transfer of "representations" of "resources".
                The central resource with respect to the Contracts Finder service is the procurement opportunity.
            </p>
            <h3>Unique provider identifier</h3>
            <p>
                There is a potential for confusion since each notice will have 2 unique identifiers.
                One is provided by the creator in a format meaningful to them and must be unique within the creating organisation.
                Another is assigned internally by Contracts Finder, which will be a GUID.
            </p>
            <p>
                So, upon creating a new notice, a unique provider identifier needs to be supplied by the creator.
                This identifier must not have been used previously by the originating organisation, otherwise a validation error occurs.
                On successful creation of a notice, a new unique identifier (in GUID form) is returned.
                This new unique reference is then used throughout the Web API to perform further operations on the notice.
            </p>
            <h3>Security and Authorisation</h3>
            <p>
                Authentication is required to access certain parts of the Web API.
                To obtain an access token you must <a href="/apidocumentation/Authentication">POST to the token endpoint</a>.
                The POST request must include a basic authorization header containing <span class="doc-code">username:password</span> in base-64 encoded format.
                It must also have a body with type <span class="doc-code">application/x-www-form-urlencoded</span> specifying <span class="doc-code">grant_type=client_credentials</span>.
                The username and password are the Sid4Gov login credentials.
            </p>
            <p>In response you are granted an access token, a sample response may look like:</p>
            <pre class="doc-code">{ "access_token":"2YotnFZFEjr1zCsicMWpAA", "expires_in":3600, "token_type":"bearer" }</pre>
            <h3>Headers</h3>
            <p>To request either JSON or XML MIME types the request needs to contain the appropriate Accept header, <span class="doc-code">application/json</span> or <span class="doc-code">application/xml</span> respectively.</p>
            <p>To access authenticated endpoints a bearer token is needed in the HTTP authorization header, this is the returned access_token described in section 2.4, for example "<span class="doc-code">bearer 2YotnFZFEjr1zCsicMWpAA</span>".</p>
            <h3>Error Handling</h3>
            <p>The standard HTTP status codes are used to indicate errors throughout the system from invalid authentication to validation errors. Please see <a href="http://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html" target="_blank">http://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html</a> for details on the status codes.</p>
            <p>For specific validation errors a 400 status code response is returned with a list of validation errors.</p>
            <p>The following is an example:</p>
<pre class="doc-code">&lt;ArrayOfValidationError&gt;
  &lt;ValidationError&gt;
    &lt;Message i:nil="true"/&gt;
    &lt;Code&gt;NotFound&lt;/Code&gt;
    &lt;Property&gt;PublishedNoticeId&lt;/Property&gt;
  &lt;/ValidationError&gt;
&lt;/ArrayOfValidationError&gt;</pre>
            <h3>Line Breaks</h3>
            <p>
                Some text fields support the use of line breaks to allow long passages to be divided into paragraphs.
                For example, the description field in notices.
            </p>
            <p>
                In order to include a line break you need to insert a CR/LF combination.
                In JSON this is encoded as "\r\n", and in XML it is encoded as "&amp;#13;&amp;#10;".
            </p>
            <h2>Mappings</h2>
            <h3>Delivery Location</h3>
            <p>The region(s) of a notice applies to the location of works for the contract - the delivery location. Providers are asked to supply either one or more regions and/or postcode and/or a region of "Any Region". The provider must supply one, but choice is dependent on preference and the scope of the delivery.</p>
            <p>Postcode information provided shall be used to look-up geo-co-ordinates and a corresponding region.</p>
            <h3>Email Addresses</h3>
            <p>Email addresses must conform with the standard pattern, i.e. similar to <span class="doc-code">given.family@domain.ext</span>. There is no further validation checking.</p>
            <h3>Country</h3>
            <p>Country must be one "name" value selected from <a href="/apidocumentation/Notices/1/GET-Country-Countries">the countries API method</a></p>
            <p>There is no further validation checking.</p>
            <h3>Dates and times</h3>
            <p>Combined date-time values are used, formatted as YYYY-MM-DDThh:mm:ss, e.g. 2014-01-29T15:09:00Z for exactly 3:09pm on 29 January 2014.</p>
            <p>The time part is included even for date-only fields.</p>
            <p>All times are local UK times, in GMT or BST depending on which is in effect on the date. Timezone information is appended to the date-time such that “Z” indicates GMT (October to March) and “+01:00” indicates BST (March to October).</p>
            <p>The time part is valid for the DeadlineDate field for notices published from 1 August 2020.</p>
            <h3>Regions</h3>
            <p>Region must be a list of one or more comma separated "name" values from <a href="/apidocumentation/Notices/1/GET-Region-Regions">the regions API method</a>. Note that API names have commas removed and accented characters changed to normal ones compared with names shown on the website. For example, "Saint Helena Ascension and Tristan da Cunha" instead of "Saint Helena, Ascension and Tristan da Cunha", "Curacao" instead of "Curaçao" and "Saint Barthelemy" instead of "Saint Barthélemy".</p>
            <h3>Type</h3>
            <p>Valid notice types are defined by <a href="/apidocumentation/ResourceModel?modelName=NoticeType">the NoticeType enumeration</a>.</p>
            <h3>OjeuContractType</h3>
            <p>Valid contract types are defined by <a href="/apidocumentation/ResourceModel?modelName=OjeuContractType">the OjeuContractType enumeration</a>.</p>
            <h3>ProcedureType</h3>
            <p>Valid procedure types are defined by <a href="/apidocumentation/ResourceModel?modelName=ProcedureType">the ProcedureType enumeration</a>.</p>
            <h3>AwardedProcedureType</h3>
            <p>A different set of procedure types is defined for awards - see <a href="/apidocumentation/ResourceModel?modelName=AwardedProcedureType">the AwardedProcedureType enumeration</a>.</p>
            <h3>AnnexDOptionType</h3>
            <p>Valid Annex D options are defined by <a href="/apidocumentation/ResourceModel?modelName=AnnexDOptionType">the AnnexDOptionType enumeration</a>.</p>
            <h3>Mime Type</h3>
            <p>Valid mime types are defined by <a href="/apidocumentation/ResourceModel?modelName=MimeType">MimeType enumeration</a>.</p>
            <h3>CPV codes</h3>
            <p>For more information on CPV codes, see <a href="http://simap.europa.eu/codes-and-nomenclatures/codes-cpv/codes-cpv_en.htm" target="_blank">http://simap.europa.eu/codes-and-nomenclatures/codes-cpv/codes-cpv_en.htm</a>.</p>
